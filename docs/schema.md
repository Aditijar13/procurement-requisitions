# Schema

The application uses MongoDB with Mongoose, so the data is stored in collections rather than SQL tables. The current schema has five main collections:

* Users
* Requisitions
* Line Items
* History Entries
* Alert Dismissals

MongoDB provides an `_id` ObjectId for each document.

## Table by table: what columns and types does each one have?

### User

The `User` collection stores the users who can access the system.

| Field            | Type       | Notes                                                    |
| ---------------- | ---------- | -------------------------------------------------------- |
| `_id`            | ObjectId   | Automatically generated by MongoDB                       |
| `name`           | String     | Required and trimmed                                     |
| `email`          | String     | Required, unique, lowercase and trimmed                  |
| `password`       | String     | Required, minimum length 6, excluded from normal queries |
| `role`           | String     | Required; either `requester` or `approver`               |
| `approval_limit` | Decimal128 | Defaults to `null`                                       |
| `department`     | String     | Required and trimmed                                     |
| `createdAt`      | Date       | Added by Mongoose timestamps                             |
| `updatedAt`      | Date       | Added by Mongoose timestamps                             |

Passwords are hashed with bcrypt before the user is saved.

---

### Requisition

The `Requisition` collection stores the main procurement requisitions.

| Field                | Type               | Notes                              |
| -------------------- | ------------------ | ---------------------------------- |
| `_id`                | ObjectId           | Automatically generated by MongoDB |
| `title`              | String             | Required and trimmed               |
| `vendor`             | String             | Required and trimmed               |
| `department`         | String             | Required and trimmed               |
| `needed_by`          | Date               | Required                           |
| `status`             | String             | Has a fixed set of allowed values  |
| `total`              | Decimal128         | Defaults to `0`                    |
| `requester`          | ObjectId           | Required reference to a `User`     |
| `assigned_approvers` | Array of ObjectIds | References `User` documents        |
| `is_archived`        | Boolean            | Defaults to `false`                |
| `createdAt`          | Date               | Added by Mongoose timestamps       |
| `updatedAt`          | Date               | Added by Mongoose timestamps       |

The allowed values currently defined in the schema for `status` are:

* `draft`
* `submitted`
* `approved`
* `rejected`
* `ordered`
* `received`

The default status is `draft`.

The requisition has indexes for text search on `title` and `vendor`, as well as separate indexes on:

* `status`
* `department`
* `needed_by`
* `is_archived`

---

### Line Item

The `LineItem` collection stores the individual items belonging to a requisition.

| Field          | Type       | Notes                                 |
| -------------- | ---------- | ------------------------------------- |
| `_id`          | ObjectId   | Automatically generated by MongoDB    |
| `requisition`  | ObjectId   | Required reference to a `Requisition` |
| `description`  | String     | Required and trimmed                  |
| `quantity`     | Number     | Required and minimum value is 1       |
| `unit_price`   | Decimal128 | Required                              |
| `received_qty` | Number     | Defaults to 0 and cannot be negative  |
| `createdAt`    | Date       | Added by Mongoose timestamps          |
| `updatedAt`    | Date       | Added by Mongoose timestamps          |

A `subtotal` is added when a line item is converted to JSON:

```text
unit_price × quantity
```

It is calculated rather than stored as a separate field.

---

### History Entry

The `HistoryEntry` collection stores actions that have happened to a requisition.

| Field         | Type     | Notes                                             |
| ------------- | -------- | ------------------------------------------------- |
| `_id`         | ObjectId | Automatically generated by MongoDB                |
| `requisition` | ObjectId | Required reference to a `Requisition`             |
| `actor`       | ObjectId | Required reference to a `User`                    |
| `action`      | String   | Required and limited to the defined action values |
| `comment`     | String   | Trimmed and defaults to an empty string           |
| `snapshot`    | Mixed    | Stores additional information about the event     |
| `created_at`  | Date     | Defaults to the current time and is immutable     |

The currently allowed history actions are:

* `created`
* `submitted`
* `approved`
* `rejected`
* `ordered`
* `received`
* `partially_received`
* `comment`
* `approver_added`
* `approver_removed`
* `archived`
* `restored`
* `reopened`

There is an index on:

* `requisition`
* `created_at`

This is used when retrieving the history for a requisition.

---

### Alert Dismissal

The `AlertDismissal` collection stores alert dismissals for users and requisitions.

| Field          | Type     | Notes                                 |
| -------------- | -------- | ------------------------------------- |
| `_id`          | ObjectId | Automatically generated by MongoDB    |
| `requisition`  | ObjectId | Required reference to a `Requisition` |
| `user`         | ObjectId | Required reference to a `User`        |
| `dismissed_at` | Date     | Defaults to the current date and time |

There is a compound unique index on:

* `requisition`
* `user`

This prevents the same user from having duplicate dismissal records for the same requisition.

## Which relationships are one-to-many, and which are many-to-many?

The application uses ObjectId references between collections.

### User to Requisition

One requester can create many requisitions.

Each requisition has one requester.

```text
User
  1
  │
  └──────< Requisition
```

This is a one-to-many relationship.

---

### Requisition to Line Item

One requisition can contain many line items.

Each line item belongs to one requisition.

```text
Requisition
      1
      │
      └──────< LineItem
```

This is a one-to-many relationship.

---

### User to Requisition as approver

A requisition can have multiple assigned approvers, and an approver can be assigned to multiple requisitions.

This is conceptually a many-to-many relationship.

The current schema represents it by storing an array of approver `User` ObjectIds in `assigned_approvers` on the requisition document instead of using a separate assignment collection.

```text
User (Approver)
       │
       │
       └──────< assigned to >────── Requisition
```

---

### Requisition to History Entry

One requisition can have many history entries.

Each history entry belongs to one requisition.

This is a one-to-many relationship.

```text
Requisition
      1
      │
      └──────< HistoryEntry
```

---

### User to History Entry

One user can appear as the actor in many history entries.

Each history entry records one actor.

This is also a one-to-many relationship.

---

### User and Requisition through Alert Dismissal

A user can dismiss alerts for multiple requisitions, and a requisition can have dismissals associated with multiple users.

The `AlertDismissal` collection represents this relationship.

```text
User
 │
 └──────< AlertDismissal >────── Requisition
```

This is conceptually a many-to-many relationship.

The compound unique index prevents duplicate dismissal records for the same user and requisition.

## Which constraints are enforced by the database, and which by application code — and why did you draw the line there?

The Mongoose schemas handle the basic structure and field-level validation.

This includes things such as:

* Required fields
* Allowed user roles
* Allowed requisition status values
* Minimum password length
* Minimum line item quantity
* Non-negative received quantities
* Required references
* Allowed history action values
* Unique user email indexes
* The unique `requisition + user` alert dismissal combination

The schemas also define indexes used for searching and retrieving data.

These rules are kept close to the models because they describe the shape of an individual document and should apply whenever that model is saved.

More complicated rules are handled in the application code, mainly in the controllers. These include:

* Only the requester can submit their own requisition
* Only draft requisitions can be submitted
* A requisition must have at least one line item before submission
* Only assigned approvers can approve or reject
* Approval is only allowed when the requisition is submitted
* An approver's approval limit must cover the requisition total
* A higher approver can be assigned when the current approver's limit is not enough
* Line items can only be changed while the requisition is a draft
* Only approved requisitions can be marked as ordered
* Only ordered requisitions can go through the receiving workflow

I drew the line there because these rules depend on more than one piece of data. They often require checking the current user, the current requisition status, related line items, or another user. That is easier to handle in the application logic than as a simple field-level schema rule.

## What did you deliberately denormalise?

The main deliberate denormalisation is the `total` field stored directly on the `Requisition`. The total is calculated on the server from the line items and then saved on the requisition.

The total can be calculated from the related line items:

```text
quantity × unit_price
```

for each line item.

The application still stores the calculated result on the requisition. When a line item is added, updated, or deleted, the line items are read again and the requisition total is recalculated and saved.

This means the total does not need to be calculated from all line items every time the requisition is displayed or checked against an approver's limit.

The `assigned_approvers` array is another deliberate design choice. Instead of having a separate collection for approver assignments, the current assigned approvers are stored directly on the requisition as `User` references.

The `snapshot` field on a history entry also stores information about an event at the time it happened. This means history can keep details such as status changes or approval information without depending only on the requisition's current state.

Line items, history entries, and alert dismissals are otherwise kept in separate collections rather than being embedded inside the requisition document.

## What would break first if this had 100x the data?

The first things I would expect to need attention are query performance and the amount of related data being loaded.

### Requisition listing

The requisition list supports searching, filtering, sorting, pagination, and populating related users.

With much more data, combinations of text search and filters could become more expensive. The current indexes provide a starting point, but the indexes would probably need to be reviewed based on the queries used most often.

### Line item total calculations

Whenever a line item is added, updated, or deleted, the application reads the line items for that requisition and recalculates the total.

This is fine for the current project size, but with much larger requisitions or many simultaneous updates, that repeated calculation could become more expensive.

### History data

History entries can grow faster than the number of requisitions because one requisition can produce many events over time.

At a much larger scale, history queries would need efficient indexing and pagination. The current index on `requisition` and `created_at` is a starting point for this.

### Related user lookups

Some requisition queries populate the requester and assigned approvers.

With a much larger number of requisitions, repeatedly loading related user information could add more database work, especially for large list pages.

### Pagination

The current requisition listing uses `skip` and `limit`.

At very large page numbers, `skip` can become less efficient. If the data grew significantly, cursor-based pagination could be considered.

The current schema is suitable for the size and scope of this project, but these areas would be the first ones I would review if the amount of data increased significantly.
